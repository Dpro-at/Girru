# Owned computers and selected synchronization

Computer coordination uses the existing relay, g1 cryptography, LAN listener and local application services. The relay has no device database, content mailbox or durable task queue. It processes live transport metadata. Deployed proxy/log retention needs a separate operational audit.

`createComputerApplication` is explicit server composition. The default server has no identity/custody provider and enrollment remains closed. `disposableLoopbackTransport` exists only for explicit temporary test composition and is refused outside NODE_ENV=test. A deployment must configure a trusted membership signing key, verified issuer/subject, a device-local keystore, encrypted coordination storage and a durable restore-generation/sequence anchor. Custody anchor advancement must atomically compare the complete expected durable anchor before advancing it; rereads reject external rollback or stale cached generations. This interface still requires an accepted cross-process custody implementation. Matching account login or a network address never enrolls a device. No environment flag substitutes for these providers.

Both computers approve a fresh key-bound pairing challenge. Approved direct endpoints are bound to the peer key, membership epoch and expiry. Listening requires an explicit owner request for an interface already approved in server configuration; wildcard and unselected interfaces are rejected. Direct failure reuses the same logical event over the existing relay. Keys, bearer credentials, approval tickets and local grants never travel.

Tasks require target-local project/model/agent bindings, a current explicit agent grant and the existing exact owner Approval. The configured runtime adapter calls normal `startTurn` admission; its server-only fence also guards tool checkpoints. An expired lease, stale membership, restore uncertainty or interrupted admission closes effects and never automatically reassigns an attempt.

Selected agent/personality/specialty/skill/rule definitions use the existing workspace control preview and approval engine. Imported rules start paused. Only explicitly selected portable interface preferences are supported. Follow is opt-in for definitions/preferences and each target update still requires review. Credential paths, provider keys, tool grants, OS bindings and local project paths are excluded.

Task-linked Board metadata, selected text messages, prepared report snapshots and bounded artifacts retain independent provenance. Imported chats have no fabricated provider run or tool checkpoint. Prepared report publication uses the existing report validator/renderer and external-prepared provenance. Artifacts use the existing guarded file writer in a separate per-record project directory; no Git commit, push, branch switch or raw folder mirroring is performed. The current per-artifact bound is 24 KiB; larger inputs are explicitly refused. Binary data is never executed or unpacked. An accepted artifact-root fencing/custody callback is required before writes.

Local review records contain versions, hashes, mappings, receipts and uncertain outcomes. Concurrent changes require explicit conflict resolution; unknown effects are never retried automatically. Full memory synchronization remains gated by accepted ENC/V3-6 privacy, forget, key epoch and restore contracts and explicit owner resume. This module does not activate or modify that implementation.

Native device requests require the current primary owner-chat context, ordinary grants and one-time approval. Exported MCP offers bounded read/request operations only, never pairing, secret transport or remote approval. Physical WiFi, original-device enrollment, real provider execution and production custody acceptance are separate from source and synthetic verification.

Desktop enrollment now composes a concrete OS vault, native Google OIDC verifier, owner-local membership signer and independently retained metadata witness. The ordinary setup flow checks OS encryption, opens Google in the system browser, creates a pinned code, and requires both computer owners to compare and approve it. The default witness root is selected by the desktop host outside the workspace and vault. Google identity does not pair computers or grant execution. Enrollment requests a fresh host challenge bound to the joining device key; its short-lived Google ID-token proof crosses only the pinned owner g1 channel for host verification, stays memory-only and is never exposed to renderer DTOs. No Google access or refresh token is transported or retained.

The public Desktop OAuth client belongs to the separate `dpro-identity` project with consent name `Dpro`; the public identifier is configurable. Device enrollment requests `openid` only. Application registration/sign-in requests `openid email` to verify the new account email; its canonical login mapping is issuer plus subject, never an email merge. First-owner Google signup retains the existing loopback setup token and SQL owner lock. Existing accounts require explicit linking, fresh current password and the existing verification policy. Password login and recovery remain available. Native OAuth is asynchronous start/status/finish; opaque one-use flow references remain POST bodies, with verified proofs held in the local backend. The application bridge handles local sessions; the device relay is not an OAuth proxy or account database.

The vault uses Electron safeStorage with feature-detected asynchronous APIs and compatible synchronous fallback. Encryption-unavailable backends, including Linux `basic_text`, are refused. Windows DPAPI and macOS Keychain do not constitute a hardware non-exportable signing key or protection from arbitrary code running as the same OS user. Device SQL projections use authenticated encrypted envelopes bound to device, table, column and row identity. Existing domain stores and whole-profile encryption remain under their existing contracts; this does not activate the paused ENC implementation.

Witness metadata contains device identities, monotonic generation/hash/sequence and replay counters only, on owner-controlled storage. It never contains tasks or credentials. A lost or uncertain first host locks the old group. Explicit fresh-owner recovery rotates keys, retains sealed history read-only and requires re-pairing; it cannot resume old unknown effects. Co-restoring every trusted root is not independently detectable: known-host provenance must be explicitly confirmed, or a new group established. Directory leases reject live/unknown writers; explicit native owner review may recover a proven dead-process lease while retaining its evidence. No protection from an arbitrary same-user writer is claimed.

Incoming tasks create one target-local pending Board card before execution approval. Immediate acceptance uses normal run admission. One-shot scheduling records the exact UTC time, displayed timezone, target card version and approved intent; the existing device queue waits until due, honors target background pause and rechecks authority, grants, membership epoch, card version and admission fences. Missed windows, stale/unknown restore and cancelled work require new review; old approval tickets are never replayed at the scheduled time.

Temporary fixtures substitute OS custody and Google consent explicitly. Those results do not establish real Keychain/DPAPI prompts, real Google consent, real-device WiFi or physical host-loss acceptance. Actual Google account interaction and selected LAN interfaces require separate owner-local trials. The relay remains the existing stateless transport, with no new central account/content registry.

Device identity and join-proof consent also use bounded asynchronous initiation, with setup status polling while the system browser is open. Closing or recovering the application invalidates late consent and business callbacks. Outer g1 signing counters are durable independently of execution checkpoints, so a witness refresh does not recursively require itself and metadata revocation can still be fetched when execution authority is unavailable.

Application Google identity currently maps to a local installation account. It does not implement a central Dpro account, hosted device registry or central presence/task routing service. A future central identity/metadata topology needs a separate approved authority, retention and deployment plan; this extension neither changes the existing relay server nor provisions such a service.
